## Как пользоваться этим файлом

- 11 разделов. Можно прочитать подряд (~20 минут), можно как справочник.
- Команды набраны моноширинным шрифтом. Текст после `#` — пояснение,
  вводить его не нужно.
- **Самое частое заблуждение новичка — перепутать, ГДЕ вводится команда.**
  Команды из гайда живут в трёх разных местах:

| Где вы находитесь | Как это понять | Что там вводится |
|---|---|---|
| 💻 **Ваш компьютер** | строка ввода начинается с `C:\Users\...` (Windows) | `git ...` — работа с кодом и версиями |
| 🖥 **Сервер (VPS)** | вы ввели `ssh root@...`, строка начинается с `root@...` | nginx, certbot, docker, `./scripts/...` |
| 🌐 **GitHub в браузере** | открыт сайт github.com | секреты, просмотр результатов Actions |

Подсказка: если в строке ввода видите `root@...` — вы «внутри сервера»,
любая команда выполняется на нём. Команда `exit` — вернуться на свой
компьютер («положить трубку»).

## 1. Вся система на одной картинке

```
 ваш компьютер            GitHub (облако)                сервер (VPS)
 ─────────────────    ────────────────────────────    ─────────────────────────
 git add / commit  →   хранит ВСЕ версии кода      →   «квартира», где сайт
 git push              Actions: CI — автопроверки      реально живёт и отвечает
 git tag v1.0.3         CD — доставка по тегу          посетителям (nginx+docker)
```

У каждого места своя роль, и путать их нельзя:

- **Компьютер** — рабочий стол. Здесь правят код, делают «снимки» (коммиты)
  и выпускают версии (теги).
- **GitHub** — облачный архив + охрана + автопилот. Хранит все версии,
  автоматически проверяет каждую («техосмотр») и умеет сам доставлять
  версию на сервер по команде-тегу.
- **Сервер** — съёмная квартира сайта. Тут живут nginx (ресепшн), Docker
  (кухня) и база данных (кладовая). Сюда сайт «переезжает» и отсюда отвечает
  посетителям.

## 2. Git — фотоальбом вашего проекта

Представьте проект как семейный фотоальбом, где вы раз в какое-то время
фотографируете **всю** папку целиком.

**Коммит — снимок + подпись.** Команда «приготовиться» — `git add .`,
«щёлк» — `git commit -m "подпись"`. Например:

```bash
git add .                            # все изменения — в кадр
git commit -m "Протокол: кнопка завершения матча"   # снимок сделан и подписан
```

Ценность в том, что **ничего не теряется**: в любой момент можно вернуться
к любому старому снимку. Красный CI на GitHub — тоже всего лишь снимок,
который «не прошёл проверку»; ваш прошлый рабочий снимок никуда не делся.

Полезные «кнопки альбома»:

| Команда | Что делает | Аналогия |
|---|---|---|
| `git status` | показывает, что изменилось с прошлого снимка | «что лежит не на месте» |
| `git log --oneline` | список всех снимков, по строке на каждый | оглавление альбома |
| `git push origin main` | выложить свежие снимки в облако GitHub | отправить альбом в облако |
| `git pull` | забрать из облака снимки, которых нет у вас | скачать свежие страницы |
| `git clone адрес` | забрать копию альбома целиком (первый раз) | купить такой же альбом |
| `git reset --hard ЭТАЛОН` | заменить мой альбом точно как эталонный | «перезаписать по образцу» |

Про `reset --hard` — в DEPLOY.md шаг А1. Звучит страшно, но по смыслу это
«выбросить мои черновики и переписать альбом по эталонной копии». В шаге А1
это осознанно и безопасно: черновики в вашем случае — только эксперименты
с DEPLOY.md, а взамен приезжает выверенная версия v3.

## 3. Теги — наклейки версий

**Проблема, которую решают теги.** Коммитов в альбоме десятки, они все
похожи («правка», «ещё правка»). А на сайте должна жить **конкретная**
версия. Нужен способ ткнуть пальцем: «вот ЭТА версия — ставим её в эфир».

**Тег — наклейка с номером, наклеенная на конкретный снимок.**

```bash
git tag v1.0.3              # наклеить наклейку «v1.0.3» на текущий снимок
git tag                     # список уже наклеенных наклеек
git push origin v1.0.3      # сообщить облаку про наклейку — ЗАПУСК ДОСТАВКИ
```

Ровно последняя команда — та самая «кнопка выката»: `git push origin v1.0.3`
будит автопилот доставки (CD), который собирает версию, везёт на сервер,
проверяет и в случае беды сам откатывает.

**Почему обычный push сайт не обновляет.** Так задумано:

| Команда | Кто просыпается | Смысл |
|---|---|---|
| `git push origin main` | только CI (проверки) | «в облако приехали снимки — прогоните техосмотр» |
| `git push origin v1.0.3` | CI уже прогнан; просыпается CD | «приказ: собрать ЭТУ версию и поставить на сайт» |

Обычный push — «положили на полку», тег — «осознанная отгрузка в эфир».
Поэтому случайные правки физически не могут «уехать на сайт» мимо вас.

**Правило трёх цифр** `v1.2.3` (старшая → младшая):

| Какая цифра | Когда меняется | Пример |
|---|---|---|
| последняя (3) | починка, мелкая правка | `v1.0.0` → `v1.0.1` |
| средняя (2) | новая функция | `v1.0.1` → `v1.1.0` |
| первая (1) | «всё радикально поменялось» | `v1.1.0` → `v2.0.0` |

**Полный ритуал выпуска версии** (на вашем компьютере, 2 команды):

```bash
git tag v1.0.3              # занят номер? см. git tag, возьмите v1.0.4
git push origin v1.0.3      # приказ доставить
```

Дальше: GitHub → Actions → строка «CD / v1.0.3» — три job'а по очереди
(Build → Deploy → проверка сайта). Вы — наблюдатель: прогресс виден в логах,
~7 минут.

**Частые казусы с тегами:**

| Ошибка | Причина | Лечение |
|---|---|---|
| `fatal: tag 'v1.0.3' already exists` | наклейка с таким номером уже висит | `git tag` → выбрать номер, которого нет (`v1.0.4`) |
| наклеили не туда / передумали | — | `git tag -d v1.0.3` (снять у себя), `git push origin :refs/tags/v1.0.3` (снять в облаке) |
| `everything up-to-date` на пуш тега | тег уже был в облаке | это не ошибка — версия уже отгружена; нужен новый номер |
| тег есть у вас, а CD молчит | тег не спушен | именно `git push origin v1.0.3`, а не просто `git push` |

## 4. GitHub Actions — охрана и автопилот

**CI — «техосмотр» на каждый push.** Каждая отгрузка снимков в облако
автоматически отправляет код на сервис-проверку. Что проверяется:

| Job | Что делает | Бытовая аналогия |
|---|---|---|
| quality | ESLint (стиль кода), tsc (типы), 54 юнит-теста | грамотность + «все детали на месте?» |
| integration | чистая база + 16 сценариев на настоящей сборке | тест-драйв на полигоне |
| docker | пробная сборка «коробки» для перевозки | упаковка всухую, без отправки |
| audit | проверка библиотек на известные дыры | СЭС-проверка продуктов |

**CD — автопилот доставки.** Спит, пока не увидит тег `v*`. Проснувшись:
собрал «коробку» (образ) → положил на склад (GHCR) → доехал до сервера →
проверил, что сайт живой (`health-check`) → при провале сам вернул прошлую
версию (откат). Прод не «лежит» даже при плохой версии.

**Как читать красный прогон** — навык важнее любой команды:

1. GitHub → вкладка **Actions** (сверху, рядом с Code).
2. Кликните на строку с красным крестиком ✕.
3. Слева — список job'ов (Lint · Typecheck · Unit, Integration…). Кликните красный.
4. Внутри — шаги. Найдите **первый красный** шаг (ниже него всё «и так бы упало»).
5. Прочитайте **последние 20–30 строк** лога — причина почти всегда
   сформулирована в самом низу человеческим языком.
6. Сверьте со «частыми ошибками» (раздел 10). Не нашли — пришлите мне эти
   строки, это и есть диагноз.

**Красный CI — это не «вы всё сломали».** Это охрана сказала: «в этой версии
есть проблема, в эфир её не пустим». Сайт тем временем спокойно работает на
прошлой проверенной версии. Зелёный CI = новая версия «допущена к отгрузке».

Странное значение вроде `-1s` в списке Actions — не поломка: запуск ещё
не начался или был отменён (например, обогнан более свежим). Обновите
страницу через минуту.

**Почему CD красный, пока вы не настроили сервер.** Автопилоту нужны адрес
«квартиры» и ключи от неё (секреты, раздел 5). Пока их нет — «курьер уехал
без адреса». После шага А1/Б8 — не ранее — красный CD пропадает сам.

## 5. Секреты GitHub — ключи под ковриком

**Зачем секреты.** Доставке нужен доступ на ваш сервер. Но пароли и ключи
нельзя класть в код (код виден всем). Поэтому значения хранят «секретами»:
Actions подставляет их только в момент работы, и никто не может прочитать
их даже в логах — на экране будет `***`.

Четыре секрета — как пропуск курьеру:

| Секрет | Что это | Аналогия |
|---|---|---|
| `DEPLOY_HOST` | IP сервера, например `194.87.15.42` | адрес дома |
| `DEPLOY_USER` | `root` | имя, под которым курьер звонит в домофон |
| `DEPLOY_SSH_KEY` | приватный SSH-ключ целиком | сам ключ от двери |
| `DEPLOY_PUBLIC_URL` | `https://footballday.ru` | куда сходить проверить результат |

### ⚠️ Кавычки: заполнять БЕЗ кавычек

GitHub сохранит **ровно то, что вы вставили**. Если вставить в кавычках —
кавычка станет частью пароля, и «дверь не откроется» с ошибкой
`Permission denied (publickey)`.

| Секрет | ✅ правильно | ❌ неправильно |
|---|---|---|
| `DEPLOY_HOST` | `194.87.15.42` | `"194.87.15.42"` |
| `DEPLOY_USER` | `root` | `'root'` |
| `DEPLOY_PUBLIC_URL` | `https://footballday.ru` | `"https://footballday.ru"` |
| `DEPLOY_SSH_KEY` | `-----BEGIN OPENSSH PRIVATE KEY-----` … `-----END OPENSSH PRIVATE KEY-----` | ключ без последней строки; лишний пробел/перевод строки в конце |

Про ключ отдельно, потому что это ловушка №1:

- вставляется **целиком**: от `-----BEGIN OPENSSH PRIVATE KEY-----`
  до `-----END OPENSSH PRIVATE KEY-----`, включая эти строки;
- скопированный не полностью ключ (без последней строки) или случайный
  пробел в конце — самая частая причина «Permission denied (publickey)»;
- проверить, что ключ рабочий, можно ещё до GitHub (на сервере, где ключ
  создан): `ssh -i ~/.ssh/deploy_key root@localhost whoami` → `root`
  без запроса пароля.

**Ошиблись при вводе секрета?** Это чинится за 30 секунд: то же меню
(Settings → Secrets and variables → Actions) → Update → вставить заново
правильно → сохранить. Секреты можно обновлять сколько угодно раз.

## 6. SSH — звонок на сервер

`SSH` — способ «дозвониться» до сервера и работать на нём, как будто сидите
за его клавиатурой.

- `ssh root@194.87.15.42` — дозвон. Первый раз спросит «continue? → yes»,
  затем пароль. **Пароль при вводе не отображается** — ни точек, ни
  звёздочек. Это не зависание: вводите вслепую и жмите Enter.
- Приглашение строки сменилось на `root@...` — вы «внутри квартиры»:
  каждая команда теперь выполняется НА сервере.
- `exit` — положить трубку, вернуться на свой компьютер.

**Пара ключей** — вместо пароля (надёжнее и нужно для автопилота):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/deploy_key -N ""
```

Эта команда «отливает» два предмета:

| Файл | Что это | Куда кладём |
|---|---|---|
| `deploy_key.pub` | «замочная скважина» — можно показывать всем | на сервер (`authorized_keys`) |
| `deploy_key` (без .pub) | сам ключ — светить нельзя, терять нельзя | в секрет `DEPLOY_SSH_KEY` |

Смысл пары: скважина публичная, ключ секретный. Подошёл ключ к скважине —
дверь открылась. `cat`ом ключ копируют ЦЕЛИКОМ (см. раздел 5).

## 7. Docker — еда едет вместе с плитой

**Проблема, которую решает Docker:** «у меня на компьютере работало!» —
а на сервере другой Linux, другие версии библиотек, и всё падает. Docker
запечатывает приложение **вместе со всей средой исполнения**: «пирог
едет вместе с духовкой».

- **Образ** — «замороженный полуфабрикат»: ваше приложение + точные версии
  всего, что нужно вокруг. Собирает его GitHub Actions по тегу и кладёт
  на склад-реестр **GHCR** (ghcr.io).
- **Контейнер** — запущенный образ: «блюдо разогрето и подаётся». На вашем
  сервере их всегда два: `scoresbox-app` (сайт) и `scoresbox-db` (база).

Полезные команды «повара» (вводятся на сервере):

| Команда | Что делает | Аналогия |
|---|---|---|
| `docker compose -f deploy/docker-compose.prod.yml ps` | кто сейчас «на плите» и в каком статусе | меню кастрюль: app и db, `healthy` = всё кипит как надо |
| `docker logs scoresbox-app --tail 100` | последние 100 строк «речи» приложения | подслушать кастрюлю |
| `docker logs scoresbox-db --tail 30` | то же про базу | подслушать кладовую |
| `docker compose -f deploy/docker-compose.prod.yml down` | выключить всё | выключить плиту |
| `docker compose -f deploy/docker-compose.prod.yml up -d` | поднять всё заново | зажечь плиту |

Важно: `./scripts/deploy.sh` руками не запускается — его вызывает автопилот
CD, передавая номер версии. Если запустить без аргумента, скрипт честно
остановится с надписью `Использование: ./scripts/deploy.sh <тег…>` —
это защита, а не поломка.

## 8. nginx и certbot — ресепшн и паспорт сайта

- **nginx** — ресепшн на входе: встречает посетителей, оформляет HTTPS,
  раздаёт статику из кэша (быстро) и направляет запросы «внутрь» — к
  приложению на `127.0.0.1:3000`. Сайт и база наружу не торчат: наружу
  смотрит только ресепшн (порты 80/443).
- `./scripts/setup-nginx.sh footballday.ru` — «зарегистрировать ресепшн
  под ваш домен». Скрипт сам пишет конфиг, включает сайт, убирает старые
  конфиги и перезагружает nginx. **Домен — параметр:** тот же скрипт с
  `scoresbox.ru` = переезд на новый домен за минуту, руками файлы править
  не нужно.
- **certbot** — «бюро паспортов»: бесплатно выдаёт SSL-сертификат
  (Let's Encrypt) — доверие браузеров и замочек 🔒 в адресной строке —
  и сам продлевает его каждые ~60 дней.
- **`502 Bad Gateway` после настройки nginx — норма до первого деплоя:**
  ресепшн уже работает, но «повар ещё не приехал» (приложение поднимет
  деплой по тегу). Не чините 502 руками — сделайте шаг деплоя.

## 9. Справочник: каждая команда из DEPLOY.md

Где вводить: 💻 = компьютер, 🖥 = сервер, 🌐 = GitHub в браузере.

| Команда | Где | Что делает | Аналогия |
|---|---|---|---|
| `whoami` | 🖥 | кто я на этом компьютере | бейдж «root» = вы хозяин квартиры |
| `cd /opt/scoresbox` | 🖥/💻 | перейти в папку | перейти в комнату |
| `ls` / `ls -l` / `ls -d` | 🖥/💻 | показать файлы / с деталями | осмотреть комнату |
| `ping 194.87.15.42` | 💻 | дозвониться ли до сервера | «дом вообще в сети?» |
| `nslookup footballday.ru` | 💻 | какой IP у домена сейчас | спросить справочную адрес дома |
| `ssh root@IP` | 💻 | подключиться к серверу | позвонить в домофон |
| `exit` | 🖥 | отключиться от сервера | положить трубку |
| `apt update` | 🖥 | обновить каталог пакетов | освежить прайс магазина |
| `apt upgrade -y` | 🖥 | поставить все обновления | купить по свежему прайсу |
| `apt install -y nginx` | 🖥 | установить программу | купить и собрать мебель |
| `curl -fsSL … \| sh` | 🖥 | скачать установщик и выполнить | доставка «под ключ» (Docker) |
| `ufw allow 80/tcp` | 🖥 | разрешить порт | впустить только курьеров входа |
| `ufw --force enable` | 🖥 | включить файрвол | закрыть подъезд, оставить списанных |
| `git clone … /opt/scoresbox` | 🖥 | забрать код на сервер | привезти альбом в квартиру |
| `git pull` | 🖥/💻 | забрать свежие снимки из облака | докупить новые страницы альбома |
| `git fetch …` | 💻 | скачать снимки, не трогая свои | забрать посылку, не вскрывая |
| `git reset --hard FETCH_HEAD` | 💻 | переписать свою версию по эталону | «перезаписать по образцу» |
| `git push --force origin main` | 💻 | перезаписать main в облаке | настойчиво переложить альбом в облаке |
| `git push origin v1.0.3` | 💻 | отправить тег | приказ «поставить версию в эфир» |
| `cp .env.example .env` | 🖥 | сделать рабочий конфиг из шаблона | переписать бланк на чистовик |
| `nano .env` | 🖥 | редактор файла (Ctrl+X → Y → Enter) | заполнить анкету ручкой |
| `openssl rand -hex 16` | 🖥 | сгенерировать случайный пароль | перетасовать колоду и записать |
| `chmod 600 .env` | 🖥 | файл видит только root | запечатать конверт |
| `grep '^SITE_URL=' .env` | 🖥 | найти строку в файле | найти строчку в анкете |
| `sed -i 's\|старое\|новое\|' .env` | 🖥 | заменить текст в файле | аккуратно поправить ручкой |
| `cat файл` | 🖥 | показать файл целиком | выложить документ на стол |
| `cat ключ.pub >> authorized_keys` | 🖥 | добавить в конец файла | прикрутить скважину к двери |
| `ssh-keygen -t ed25519 …` | 🖥 | создать пару ключей | отлить ключ + скважину |
| `certbot --nginx -d домен` | 🖥 | получить SSL | оформить паспорт на дверь |
| `curl -I https://домен` | 💻 | «постучаться» в сайт, глянув код ответа | кивнуть охране и посмотреть ответ |
| `curl -s …/api/health` | 💻/🖥 | спросить «ты жив? что с базой?» | спросить самочувствие |
| `docker compose … ps` | 🖥 | статус контейнеров | меню кастрюль |
| `docker logs … --tail 50` | 🖥 | логи контейнера | подслушать кастрюлю |
| `crontab -e` / `crontab -l` | 🖥 | редактор / список задач по расписанию | завести будильник / посмотреть будильники |
| `./scripts/backup-db.sh` | 🖥 | снять копию базы | сфотографировать кладовую |
| `mv /opt/a /opt/b` | 🖥 | переименовать папку | переклеить табличку на двери |
| `tail -100 файл` | 🖥 | последние 100 строк файла | читать журнал с конца |

## 10. Частые ошибки: симптом → причина → лечение

| Симптом | Что случилось | Лечение |
|---|---|---|
| `./scripts/setup-nginx.sh: No such file or directory` | на сервере старая версия кода (файл появился в v3) | шаг А1 в DEPLOY.md: обновить код, затем перезапустить скрипт |
| `Permission denied (publickey)` в job Deploy | ключ в `DEPLOY_SSH_KEY` неверен или скопирован не целиком | вставить заново: без кавычек, от `-----BEGIN` до `-----END` включительно |
| Job Deploy падает: пустой host/user | секрета нет или кавычки в значении | Б8: значения без кавычек |
| `fatal: tag 'v1.0.3' already exists` | номер версии занят | `git tag` → выбрать `v1.0.4` |
| `git push` отклонён (`rejected`, `non-fast-forward`) | в облаке есть снимки, которых нет у вас | по шагу А1: `git fetch` + `git reset --hard` + `git push --force` |
| Красный CI | версия не прошла «техосмотр» | раздел 4: первый красный шаг, последние 30 строк лога |
| Красный CD на каждом push | старая версия cd.yml: доставка запускалась на каждый push; в v3 — только по тегу | обновиться до v3 (А1) |
| `-1s` в списке Actions | запуск отменён/ещё не начался | обновить страницу через минуту |
| `502 Bad Gateway` | ресепшн работает, приложение не поднято | `docker logs scoresbox-app --tail 50`; деплой по тегу ещё не сделан? |
| `Использование: ./scripts/deploy.sh <тег…>` | скрипт запущен без аргумента | это не ошибка: деплой запускается тегом, не руками |
| Домен ведёт не туда | DNS ещё не обновился | `nslookup домен`, подождать до 1 часа |
| `git clone` просит пароль | репозиторий приватный | сделать public или клонировать по токену |
| CI зелёный, а сайт старый | не выпущен тег | `git tag vX.Y.Z && git push origin vX.Y.Z` |

## 11. Мини-словарь

| Термин | Простыми словами |
|---|---|
| репозиторий (repo) | папка проекта + вся его история версий |
| коммит | снимок проекта с подписью |
| ветка | параллельная версия альбома; `main` — основная, «в эфире» |
| тег (v1.0.3) | наклейка с номером на конкретном снимке; приказ к доставке |
| push / pull | выложить в облако / забрать из облака |
| clone | забрать копию репозитория целиком |
| GitHub | облако для кода + проверки + автодоставка |
| Actions | автопроверки (CI) и автопоставка (CD) на GitHub |
| CI | «техосмотр» кода на каждый push |
| CD | «автопилот» доставки версии на сервер по тегу |
| образ | приложение, запечатанное со всей средой («пирог с духовкой») |
| контейнер | запущенный образ («блюдо подаётся») |
| GHCR | склад готовых образов на GitHub |
| секрет | скрытая переменная (пароль/ключ), видна только Actions |
| `.env` | файл настроек и паролей проекта на сервере |
| health-check | автоматический вопрос «ты жив?» сайту после деплоя |
| откат (rollback) | автоматический возврат прошлой рабочей версии |
| бэкап | копия базы данных на случай беды |
| миграция | приведение таблиц базы к новой версии кода |
| DNS | «справочная» интернета: домен → IP |
| SSL-сертификат | «паспорт доверия» сайта для браузеров (замок 🔒) |
| IP | числовой адрес сервера в интернете |
| root | хозяин сервера, «суперключи от квартиры» |
| SSH | защищённый «звонок» на сервер; ключ = пропуск |

*Ошибок не бойтесь: красный прогон — это охрана, отработавшая как надо.
Сломать «намертво» в этой схеме почти ничего нельзя: есть бэкапы, откат
и проверенные версии в облаке. Читать логи — навык №1 (раздел 4), остальное
приложится.*
