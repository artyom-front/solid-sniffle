# 📊 SCORESBOX · Глубокая аналитика проекта

**Дата:** 03.09.2026 · **Аудитория:** владелец проекта и будущая команда разработки
**Предмет:** спортивно-аналитический портал «Футбол Чувашии» (livescore, таблицы, статистика, админка)
**Текущий домен:** `footballday.ru` (временный, до получения доступа к `scoresbox.ru`)

Этот документ — «карта местности» по проекту: что внутри, насколько это надёжно,
куда расти и какие грабли разложены по дороге. Сопровождает DEPLOY.md (как ставить)
и дополняет его ответом на вопрос «почему сделано так и что будет дальше».

**Три главных вывода.**

1. **Проект зрелый для запуска.** Связка Next.js SSR + PostgreSQL + Docker + CI/CD
   с автотестами и авто-откатом — это уровень команд из десятков человек, упакованный
   в кодовую базу одного человека. Для регионального портала с аудиторией в тысячи
   посетителей в день текущей архитектуры хватит с большим запасом.

2. **Главный риск — не код, а инфраструктура.** Единственный VPS и бэкапы на том же
   диске означают: отказ диска = потеря всего, включая копии. Это единственный пункт,
   который стоит чинить не «когда-нибудь», а в первую неделю после запуска (см. P0 в дорожной карте).

3. **Смена домена — штатная операция.** Домен вынесен в переменные (`.env SITE_URL`,
   `scripts/setup-nginx.sh <домен>`, секрет `DEPLOY_PUBLIC_URL`); единственная «правка в коде» —
   строка `DOMAIN` в `brand.ts` (надпись в подвале). Переезд с footballday.ru на scoresbox.ru
   займёт ~15 минут без потери данных.

## 2. Технологический стек и карта кода

### 2.1 Стек и обоснование выбора

| Слой | Технология | Почему выбрано | Альтернатива, от которой отказались |
|---|---|---|---|
| Фреймворк | Next.js 16 (App Router) | SSR для SEO + React-компоненты для интерактива; один фреймворк вместо «сайт отдельно, API отдельно» | Чистый React (нет SSR → хуже SEO), отдельный Express-сервер (два деплоя) |
| Язык | TypeScript (strict) | Ошибки ловятся до запуска; типы — документация | JS (быстрее писать, дороже поддерживать) |
| UI | Tailwind CSS 4 + shadcn/ui (Radix) | Готовые доступные компоненты, единый дизайн-язык | Свой CSS-фреймворк (месяцы работы) |
| БД | PostgreSQL 16 | Транзакции для турниров (таблицы = агрегаты), надёжность, pg_dump | SQLite (не переживает одновременные записи судей и просмотры) |
| ORM | Prisma 6 | Типизированные запросы = ошибки в SQL ловит компилятор | Сырой SQL (быстрее, но типы не проверить) |
| Рантайм | Bun | Быстрый старт контейнера, меньше RAM, `bun test` | Node.js (медленнее холодный старт) |
| Контейнеры | Docker (multi-stage, standalone) | «Работает у меня — работает на сервере»; образ собирает CI | npm install на сервере (ад версий зависимостей) |
| CI/CD | GitHub Actions + GHCR | Бесплатно для public-репо, интеграция с репозиторием | Jenkins/GitLab (свой сервер, обслуживание) |
| Прокси | Nginx на хосте + certbot | TLS и продление сертификатов вне контейнеров — нет «курицы и яйца» при старте | Nginx в докере (сложнее порядок запуска SSL) |

**Вывод:** стек консервативен в хорошем смысле — каждая позиция либо
industry-стандарт, либо осознанный компромисс с записанной причиной. Экзотики нет,
значит любую проблему гуглится за минуты, а новый разработчик вольётся быстро.

### 2.2 Карта директорий

```
src/
├─ app/
│  ├─ (site)/          ← публичный портал: /, /match/[id], /league/[id],
│  │                      /team/[id], /player/[id], /stadium/[id] — все SSR
│  ├─ admin/           ← панель управления (RBAC, 2FA)
│  ├─ api/             ← 46 REST-роутов: public/, admin/, auth/, health
│  ├─ sitemap.ts       ← карта сайта из БД (матчи/лиги/команды/игроки)
│  └─ robots.ts        ← закрывает /admin и /api от индексации
├─ components/portal/  ← SiteShell, AdminShell, брендинг (brand.ts), UI-примитивы
├─ lib/
│  ├─ engine/          ← ⭐ бизнес-ядро: schedule, standings, discipline,
│  │                      lifecycle, signals, stats — чистые функции, тестируются unit-ами
│  ├─ auth.ts          ← сессии: scrypt + HMAC-cookie
│  ├─ totp.ts          ← 2FA: RFC 6238, анти-replay, резервные коды
│  ├─ queries.ts       ← выборки Prisma (include — без N+1)
│  └─ seo.tsx          ← JSON-LD (schema.org) + canonical
prisma/schema.prisma   ← 16 моделей домена
tests/                 ← unit (5 файлов) + integration (16 API-тестов)
scripts/               ← deploy.sh, rollback.sh, backup-db.sh, setup-nginx.sh
deploy/                ← docker-compose.prod.yml, nginx.conf
.github/workflows/     ← ci.yml (4 job), cd.yml (build→deploy→health-check)
```

**Принцип, который стоит удерживать:** вся бизнес-логика живёт в `lib/engine/*`
чистыми функциями (вход → выход, без обращения к БД), а роуты и страницы лишь
«склеивают» движки с выборками. Это делает ядро проверяемым изолированно и
позволяет менять UI, не трогая правила турниров.

## 3. Архитектура: слои и поток данных

### 3.1 Слои

```
                БРАУЗЕР / ПОИСКОВИК
                        │  HTTPS
                ┌───────▼────────┐
                │  NGINX (хост)  │  TLS, gzip, кэш /_next/static 30 дней
                └───────┬────────┘
                ┌───────▼────────┐
                │ NEXT.JS (Bun)  │  SSR-HTML + REST API
                │  app/(site)    │  ISR: матч 30 с, лига 60 с,
                │  app/api/*     │        команда/игрок 120 с, стадион 300 с
                └───┬─────────┬──┘
        lib/engine ─┘         └─ lib/queries (Prisma)
        (чистые правила)             │
                                 ┌───▼────┐
                                 │POSTGRES│  16 таблиц, том pgdata
                                 └────────┘
```

Поток данных на запрос страницы матча: nginx → Next.js проверяет ISR-кэш
(страница пересобирается не чаще раза в 30 секунд) → при промахе `queries.ts`
делает выборку с `include` (один SQL-запрос со связями, без N+1) → движки
`engine/lifecycle` и `engine/stats` обогащают данные → рендерится HTML с
JSON-LD разметкой SportsEvent. Поисковик получает готовый контент без выполнения
JavaScript — это и есть SSR-преимущество для портала, чей трафик приходит из поиска.

### 3.2 Стратегия рендерининга — осознанный компромисс

| Страница | Режим | Период обновления | Почему |
|---|---|---|---|
| Главная (livescore) | force-dynamic | каждый запрос | live-счёт должен быть свежим всегда |
| Матч | ISR | 30 с | во время игры счёт «почти live» без нагрузки на БД |
| Лига | ISR | 60 с | таблицы меняются по ходу тура |
| Команда / Игрок | ISR | 120 с | составы и статистика меняются редко |
| Стадион | ISR | 300 с | справочная страница |

Система ISR — главный «двигатель экономии»: страницу матча может открыть
10 000 человек во время игры, но БД при этом опрашивается не чаще 2 раз в минуту.
Каждый следующий запрос до истечения срока обслуживается из кэша за миллисекунды.
Это ровно тот механизм, который позволяет порталу держать пиковую нагрузку
на дешёвом VPS.

### 3.3 Модель данных

16 таблиц домена покрывают полный цикл турнира: `League → Season → Team/Club →
Person (игрок/судья/тренер в одной сущности) → Match → Event (голы, карточки) →
Suspension (дисквалификации) → Standing (таблица)`. Спроектирована вокруг
инвариантов (например: «дисквалификация начинается после N жёлтых карточек»,
«техпоражение = 0:3 и очки по регламенту») — эти правила закодированы в
`engine/discipline` и `engine/standings` и зафиксированы тестами.

Замечание на будущее: связь «один Person — одна запись» при смене команды
реализована через записи по сезонам — правильное решение, но требующее
дисциплины при вводе данных операторами (дубли людей — типичная проблема
краудсорс-порталов; движок `admin/merge` для склейки дублей уже есть).

### 3.4 Аутентификация и сессии

Сессии — stateless: cookie подписана HMAC (`AUTH_SECRET`) и содержит данные
пользователя, поэтому проверка сессии не требует похода в БД на каждый запрос
(дёшево при росте трафика). Пароли — scrypt (память-тяжелая функция, GPU-брутфорс
дорог). 2FA — TOTP по RFC 6238 с защитой от повторного использования кода и
восемью одноразовыми резервными кодами. Rate-limit на `/api/auth/login` и
`/api/auth/otp` (ответ 429) ограничивает перебор.

Слабое место текущей реализации rate-limit — счётчики в памяти процесса:
при горизонтальном масштабировании (2+ инстансов приложения) лимиты считались бы
независимо. Для одного инстанса — корректно; в дорожной карте (P2) — Redis.

## 4. Безопасность

### 4.1 Инвентаризация механизмов

| Механизм | Реализация | Оценка |
|---|---|---|
| Хэш паролей | scrypt (memory-hard) | ✅ современно, устойчиво к GPU |
| Cookie-сессии | httpOnly + подпись HMAC (AUTH_SECRET) | ✅ не крадётся JS, не подделывается |
| 2FA | TOTP RFC 6238, окно ±1, анти-replay, 8 резервных кодов | ✅ полный набор |
| Брутфорс | rate-limit на login/otp → 429 | ✅ (в памяти процесса — см. P2) |
| Роли | RBAC: SUPER_ADMIN / админ лиги / админ клуба / судья | ✅ разделение полномочий |
| Аудит | таблица действий администраторов (`admin/audit`) | ✅ «кто что сделал» |
| Секреты | `.env` вне git, `chmod 600`, отдельный SSH-ключ деплоя | ✅ |
| TLS | Let's Encrypt + автопродление (certbot) | ✅ |
| Зависимости | `bun.lock` (фиксация версий) + job audit в CI | ✅ |
| Заголовки | nosniff, X-Frame-Options SAMEORIGIN, Referrer-Policy | ✅ в nginx |

Итог по приложению: для проекта частной разработки покрытие необычно полное —
обычно 2FA и аудит появляются сильно позже. Дыр в коде, требующих немедленного
патча, аудит не выявил.

### 4.2 Что усилить (инфраструктура)

- **Файрвол UFW** — сейчас на VPS открыты все порты, которые слушают службы;
  приложение и БД привязаны к localhost, но явный «deny by default» надёжнее.
  Три команды в DEPLOY.md (раздел «укрепление») — 5 минут работы.
- **Деплой от root** — GitHub Actions входит как root. Бlast radius: CI-ключ
  может выполнить на сервере что угодно. Правильный паттерн — отдельный
  пользователь `deploy` с ограниченными правами (P1 в дорожной карте).
- **Fail2ban** — пароли перебирают и через SSH; лимит попыток по журналу
  auth.log ставится одной установкой (P1).
- **Приватность образа GHCR** — если репозиторий приватный, образ тоже приватный,
  и `docker login` на сервере при откате потребует живого токена. Для публичного
  репо проблемы нет.

## 5. Масштабируемость

### 5.1 Сколько выдержит текущая конфигурация (1 VPS, 2 ГБ, 1 vCPU)

Оценки консервативные, по ёмкости ISR-кэша и типа нагрузки:

| Сценарий | Нагрузка | Вердикт |
|---|---|---|
| Обычные будни сезона | ~1–5 req/s, 90%+ из кэша ISR | запас ×20 и более |
| Турнирный день (пик) | ~10–30 req/s, страницы матча | запас ×3–5; БД почти не ощущает |
| Матч-сенсация + СМИ | 100+ req/s | упрёмся в CPU SSR; пора Этап 2 |

Ориентир в цифрах трафика: 10 000 уникальных посетителей в день для портала —
это в среднем 0,3 req/s с всплесками до 5–10 в часы игр. **Вывод: до ~30–50 тыс.
посетителей в день текущий сервер справляется без изменений.** Столько читает
футбол Чувашии в самом оптимистичном прогнозе — запас спроектирован с избытком.

### 5.2 Узкие места (ранжировано по опасности)

1. **Единственный VPS** — отказ диска/CPU/сети = полный простой сайта и админки.
   Не вопрос «если», а «когда»: у железа конечная надёжность.
2. **Бэкапы на том же диске** — усиливает пункт 1: простой превращается в потерю
   данных. Единственный риск с необратимыми последствиями.
3. **Нет мониторинга** — о падении вы узнаёте от пользователей. Простои длятся
   дольше необходимого.
4. **БД и приложение на одном хосте** — делят 2 ГБ RAM и 1 vCPU; тяжёлые отчёты
   админки могут «подлагивать» live-страницы.
5. **Rate-limit в памяти** — блокирует горизонтальное масштабирование (см. 3.4).
6. **`prisma db push` вместо миграций** — схема обновляется без истории изменений;
   при появлении второго разработчика конфликты схем станут рутиной (P1).

### 5.3 План роста: три этапа с триггерами

**Этап 0 — сейчас (до ~30 тыс. визитов/день).** Ничего не масштабировать.
Сделать P0 из дорожной карты (offsite-бэкап, мониторинг, UFW) — это не масштаб,
это страховка. Стоимость владения ~270 ₽/мес не меняется.

**Этап 1 — рост (30–100 тыс. или жалобы на скорость).**
- CDN перед nginx (Cloudflare, бесплатный тариф): статика и ISR-страницы
  отдаются с узла рядом с пользователем, TLS на edge, VPS разгружается от 60–80% трафика.
- VPS → 4 ГБ RAM / 2 vCPU (~500 ₽/мес).
- Бэкапы → в объектное хранилище (если не сделано в P0).
- Триггер перехода: `uptime`-монитор фиксит p95 > 800 мс или CPU > 70% две недели подряд.

**Этап 2 — зрелость (100 тыс.+ / регулярные пики СМИ).**
- Managed PostgreSQL (Timeweb/Selectel) — БД переживает падение VPS, бэкапы и
  реплики на стороне провайдера.
- Второй инстанс приложения: в nginx уже есть блок `upstream scoresbox_app`
  с keepalive — добавить строку `server 127.0.0.1:3001;` (или вынести на второй VPS)
  и балансировка заработает; контейнеры без состояния (сессии в cookie) — ничего
  переписывать не надо.
- Redis: rate-limit и общий кэш между инстансами.
- Триггер: Этап 1 не снял пики, или SLA важнее экономии.

Сильная сторона проекта: **вертикального масштабирования и CDN хватит до
очень серьёзных нагрузок**, а «кнопки» горизонтального (upstream, stateless-сессии,
ISR) уже вшиты в архитектуру — включать их придётся по одной, без рефакторинга.

## 6. Производительность и надёжность

### 6.1 Что уже сделано «из коробки»

| Механизм | Эффект |
|---|---|
| ISR 30–300 с | страница матча собирается максимум 2 раза в минуту, отдаётся из кэша |
| `bun` + standalone-сборка | контейнер весит меньше и стартует за секунды; после рестарта VPS портал поднимается сам (`restart: unless-stopped`) |
| gzip в nginx | HTML/JSON/JS/CSS сжимаются в 3–5 раз |
| кэш `/_next/static` 30 дней immutable | статику браузер запрашивает один раз |
| keepalive 32 в upstream | nginx переиспользует соединения к приложению — нет цены TCP-хендшейка на каждый запрос |
| health-check `/api/health` | дёшево (один `count`), проверяет и приложение, и БД; используется деплоем и мониторингом |

### 6.2 Отказоустойчивость: цифры

- **RPO** (сколько данных теряем при аварии) = до 24 часов: ночной `pg_dump` в 03:15.
  Сокращается до ~1 часа переносом бэкапа в облако сразу после снятия (P0).
- **RTO** (сколько восстановимся) = 10–15 минут: `pg_restore` + `docker compose up`
  по инструкции из DEPLOY.md; сценарий отрепетирован командами в гайде.
- **Авто-откат деплоя**: если новая версия не проходит health-check за 90 секунд,
  `deploy.sh` возвращает предыдущую рабочую — релиз не «кладёт» прод в ожидании админа.
- **SSL-сертификаты** продлеваются сами (certbot-timer); проверка `certbot renew --dry-run`
  — в чек-листе диагностики.

### 6.3 Чего не хватает для «настоящего SLA»

Мониторинг и оповещения. Сейчас о проблеме узнают: а) вы, зайдя на сайт,
б) пользователи. Пороги и инструменты — в разделе 9; смета бесплатная.

## 7. Качество и тестирование

| Слой | Что проверяется | Инструмент |
|---|---|---|
| Бизнес-ядро | круговое расписание, таблицы, дисквалификации, сигналы — 54 unit-теста | `bun test tests/unit` |
| HTTP-контракт | 16 integration-тестов против живого сервера + чистой БД: REST, 2FA-флоу, SSR/SEO-заголовки | `tests/integration` |
| Инварианты PRD | 36 правил (техпоражение 0:3, лимиты карточек, анти-replay OTP…) | внутри тех же тестов |
| Стиль и типы | ESLint + tsc на каждый push | job quality |
| Сборка | Docker-образ собирается | job docker |
| Зависимости | известные CVE | job audit |

Защита работает так: красный CI = Pull Request не вливается; тег версии с
красным CI в принципе не доходит до сборки образа. Прод получает только артефакт,
прошедший все четыре ступени.

Замечание: интеграционные тесты гоняются против контейнерного PostgreSQL —
то, что ловит именно класс ошибок «работает в SQLite, падает в Postgres»,
исключено по построению (единый движок БД в dev/CI/прод).

## 8. Реестр рисков

| # | Риск | Вер-ть | Урон | Митигация |
|---|---|---|---|---|
| 1 | Отказ диска VPS | средняя | **катастрофа**: сайт + бэкапы | P0: offsite-бэкапы (объектное хранилище) |
| 2 | Тихая смерть cron-бэкапа | средняя | рост RPO до ∞ | P0: мониторинг бэкапа (healthchecks.io) |
| 3 | Взлом через SSH-перебор | средняя | компромисс сервера | ufw + fail2ban (P0/P1), ключи вместо пароля |
| 4 | Утечка `.env` (AUTH_SECRET/пароль БД) | низкая | подделка сессий | права 600, файл вне git, ротация при инциденте |
| 5 | Плохой релиз прошёл CI | низкая | простой до отката | уже закрыто: health-check + авто-откат |
| 6 | DNS-сбой регистратора | низкая | сайт недоступен | запасной TTL 3600; мониторинг заметит |
| 7 | Сертификат не продлился | низкая | браузеры блокируют сайт | certbot-timer + `--dry-run` в чек-листе |
| 8 | Рост объёма БД (сезоны копятся) | низкая | замедление выборок | индексы уже в схеме; контроль размера БД (раздел 9) |
| 9 | Компрометация GITHUB_TOKEN/GHCR | низкая | подмена образа | секрет живёт только в Actions, репо-политика PAT |
| 10 | Уход единственного разработчика | — | bus-factor | этот документ + DEPLOY.md + комментарии в коде |

Граф зависимостей рисков: №1 и №2 усиливают друг друга (нет внешней копии =
нет страховки от «тихого» отказа бэкапа). Поэтому P0 закрывает их парой команд
одного порядка стоимости — три минуты настройки против потенциальной потери
всей истории турниров.

## 9. Дорожная карта рекомендаций

### P0 — первая неделя после запуска (страховки, ~0 ₽)

1. **Бэкапы вне сервера.** После `pg_dump` копировать дамп в объектное хранилище
   (Timeweb Cloud / Yandex Object Storage, ~1–3 ₽/мес за гигабайт).
   Одна строка в `backup-db.sh`: `rclone copy` или `mc cp`.
2. **Мониторинг доступности.** UptimeRobot (бесплатно): ping `https://<домен>/api/health`
   раз в 5 минут, e-mail при падении. Инструмент «тихой смерти»: healthchecks.io
   следит, что cron-задание бэкапа вообще исполнилось.
3. **Файрвол.** `ufw allow 22,80,443 && ufw enable` — сетевая дверь закрыта для
   всего, кроме SSH/HTTP/HTTPS (команды в DEPLOY.md).

### P1 — первый месяц (гигиена роста)

4. **Prisma Migrate вместо db push** — история миграций в git, безопасные
   скелетные откаты схемы, почва для второго разработчика.
5. **Пользователь deploy вместо root** — CI входит ограниченной учёткой
   (права на /opt/scoresbox и docker), blast radius сужается от «весь сервер» до «проект».
6. **Fail2ban** — лимит неудачных SSH-попыток по журналу.
7. **Логи в одном месте** — `docker logs --since 24h` в файл + ротация, либо
   loki/grafana, если захочется красиво.

### P2 — по триггерам роста (когда возникнут, см. 5.3)

8. **CDN** (Cloudflare free) — по метрикам p95/CPU.
9. **Managed PostgreSQL** — к отказу «терпеть нельзя».
10. **Второй инстанс приложения** — строка в upstream + Redis для rate-limit.
11. **Ежедневный smoke-тест восстановления** — раз в неделю восстанавливать
    вчерашний дамп в temp-базу (скрипт ~20 строк); бэкап, который не проверен,
    не бэкап.

### Метрики, которые стоит смотреть (все бесплатно)

| Метрика | Где | Порог тревоги |
|---|---|---|
| Доступность `/api/health` | UptimeRobot | любой downtime |
| p95 времени ответа | UptimeRobot / CDN | > 800 мс |
| CPU/RAM контейнеров | `docker stats` | CPU > 70% постоянно |
| Место на диске | `df -h` | < 20% свободно |
| Размер БД | `SELECT pg_database_size(...)` | рост > 30% за месяц |
| Свежесть бэкапа | `ls -l backups/` | нет дампа за сегодня |
| Срок сертификата | `certbot certificates` | < 14 дней |

## 10. Шпаргалка: что нужно знать о проекте

### 10.1 Переменные окружения (`.env` на сервере)

| Переменная | Назначение | Где используется |
|---|---|---|
| `POSTGRES_PASSWORD` | пароль БД | контейнеры db/app, DATABASE_URL собирается сама |
| `AUTH_SECRET` | ключ HMAC-cookie | подлинность сессий (генерировать `openssl rand -hex 32`) |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | первый супер-админ | создаётся один раз при первом деплое |
| `SITE_URL` | **главный доменный переключатель** | sitemap, robots, canonical, OG, metadataBase |
| `SHOW_DEMO_ACCOUNTS` | демо-логины на странице входа | в проде — 0 |

### 10.2 Где живёт домен (пять мест, все задокументированы)

| Место | Как меняется |
|---|---|
| DNS у регистратора | A-запись `@` → IP сервера |
| nginx | `sudo ./scripts/setup-nginx.sh <новый-домен>` |
| SSL-сертификат | `certbot --nginx -d <новый> -d www.<новый>` |
| `.env` → `SITE_URL` | `sed -i 's|^SITE_URL=.*|SITE_URL=https://<новый>|' .env` |
| GitHub Secret `DEPLOY_PUBLIC_URL` | Settings → Secrets → Actions |
| Подвал сайта (косметика) | `src/components/portal/brand.ts` → `DOMAIN` (одна строка, уходит с релизом) |

### 10.3 Скрипты проекта

| Скрипт | Что делает |
|---|---|
| `scripts/setup-nginx.sh <домен>` | конфиг nginx под домен + включение + reload |
| `scripts/deploy.sh <тег>` | поставка версии: бэкап → миграции → up → health → откат при провале (вызывает GitHub Actions) |
| `scripts/rollback.sh` | откат на предыдущую рабочую версию |
| `scripts/backup-db.sh` | pg_dump + ротация 30 дней (вешается в cron) |
| `scripts/make-archives.sh` | пересборка доставочных архивов (bundle/zip) |

### 10.4 Роли и доступы

- **SUPER_ADMIN** — всё, включая слияние дублей и настройки безопасности;
- **админ лиги** — свои лиги/сезоны/матчи/протоколы;
- **админ клуба** — заявки и данные своего клуба;
- **судья** — протоколы своих матчей.

Демо-аккаунты (только локальная разработка): `admin@ff21.ru`, `liga@ff21.ru`,
`sudya@ff21.ru`, `club@ff21.ru` — пароли в `prisma/seed.ts`, в проде не создаются
(`SHOW_DEMO_ACCOUNTS=0`).

### 10.5 Типовые операции (по одной команде)

```bash
# логи приложения/базы
docker logs scoresbox-app --tail 100
# статус контейнеров
docker compose -f deploy/docker-compose.prod.yml ps
# история версий
cat /opt/scoresbox/.deploy/history
# ручной бэкап
/opt/scoresbox/scripts/backup-db.sh
# откат
cd /opt/scoresbox && ./scripts/rollback.sh
```
